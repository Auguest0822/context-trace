# 言迹 ContextTrace：项目整体工作流程

> 状态：产品与数据流程设计，供团队评审。接口字段和错误语义以同目录的 `api-data-contract.md` 为准。当前仓库尚未实现本文流程。

## 1. 产品目标

把用户**主动提供**的聊天记录保存为可查看的原始记录，再从选定消息中提炼可追溯记忆。用户可以跨平台浏览已归档对话、检查并确认候选记忆、按来源范围检索记忆，最后选择实际交给 Agent 的上下文。两周版本优先完成**网页 + MCP**，用手动导入或宿主实际提供的导出内容建立原始档案；浏览器扩展在这条闭环通过验收后开发。

```text
来源（两周内：手动导入 / Agent 宿主实际提供的导出；后续：浏览器扩展）
  → 用户确认归档内容
  → 原始对话与消息归档
  → 用户选择消息，预览候选记忆
  → 用户确认，记忆写入 seekdb
  → 按范围检索、查看出处与取舍理由
  → 用户在网页选择最终上下文并复制；Agent 可通过 MCP 搜索和写入记忆
```

采集、提炼、检索和注入是不同动作。保存原始对话**不会自动把整段对话变成记忆**，检索到记忆也**不会自动发送给聊天网站**。

## 2. 两种来源如何接入

### 2.1 两周内：手动导入与 Agent 宿主导出

仓库样例 JSON 和用户主动提交的聊天记录经同一归档 API 写入 `Conversation` 与 `Message`。页面显示真实提供的来源平台、标题、角色、顺序和采集完整度；手动导入没有原网页链接时 `source_url` 为 `null`。Agent 宿主只有在可靠地提供对话消息时才能归档，MCP/Skill 本身不具备读取全部历史的权限。

### 2.2 后续：浏览器扩展

网页 + MCP 闭环完成后，扩展可逐个支持用户打开并授权的 DeepSeek、Kimi、豆包网页。扩展分别用站点适配器读取**当前页面实际可取得**的对话标题、消息角色、正文、顺序和页面 URL。用户勾选消息或确认当前可见对话后，扩展显示预览，再调用归档 API。

扩展不能默认取得账户的所有历史会话；尚未加载到页面的消息、被折叠的内容或平台服务端数据均不能当作已采集。应记录 `capture_completeness`（`selected` 或 `visible_page`），并提示抓取缺失或失败。页面改版导致适配器失效时，不以空记录或残缺记录冒充成功。权限只覆盖明确支持的网站。

### 2.3 Agent：区分记忆工具与对话归档

| 能力 | 接入方式 | 能得到什么 |
| --- | --- | --- |
| 记忆读写 | MCP 工具 + Skill 使用说明 | Agent 在当前任务中主动搜索或写入**明确传给工具**的内容 |
| 完整或选定对话归档 | 宿主的导出、事件 Hook、插件接口，或用户主动选择并提交 | 宿主实际提供的消息及其会话标识 |

安装 Skill 只提供“何时调用工具”的规则；安装 MCP 只提供工具通道。它们本身不授予服务端读取宿主全部聊天历史的能力。若宿主没有可靠的对话导出接口，首版仅支持记忆读写，网页中的该 Agent 来源不显示为“已自动归档”。需要归档时由用户通过宿主提供的导出能力或手动导入完成。

## 3. 两类核心数据

| 数据层 | 内容 | 为什么单独保存 |
| --- | --- | --- |
| 原始对话档案 | 平台、会话标题、平台会话 ID/URL、采集方式、采集完整度、消息角色/正文/顺序 | 让用户跨 DeepSeek、Kimi、豆包和 Agent 查看自己保存的记录 |
| 提炼后的记忆 | 类别、独立陈述、摘要、状态、embedding、所属对话/消息、证据原文 | 支持跨会话检索、压缩、版本替换和溯源 |

一段对话可以没有记忆，也可以产生多条记忆；一条记忆可以由同一对话中的多条消息支撑。每条聊天来源的记忆必须记录 `conversation_id`、`source_message_ids`、`source_excerpt`。点击记忆可以定位到对应消息。文档、Git 或手动写入的记忆没有 `conversation_id`，仍需有效的 `source_ref` 和证据原文。

数据存入 seekdb。Python 后端负责校验、去重、抽取、分类、embedding、检索与预算选择；网页负责展示、筛选、确认、人工修正和查看来源。LLM/embedding API 是可配置的处理依赖，不直接决定“归档成功”或绕过用户确认。没有可用抽取模型时，原始对话仍可归档，候选提炼应明确报错或由用户手动写入。

## 4. 用户完整操作流程

### A. 归档对话

1. 两周版本由用户手动导入选定聊天，或由 Agent 宿主提供其确实可导出的消息；后续浏览器扩展提供网页选取入口。
2. 导入前预览将保存的消息、来源平台与完整度；用户确认后上传。
3. 后端在同一 scope 下保存 Conversation 与 Message，并返回内部 `conversation_id`。重复点击依靠幂等键和消息外部 ID 去重。
4. 网页“对话”页可按平台、标题和时间筛选，进入详情查看原始消息。

### B. 从选定消息提炼记忆

1. 用户在对话详情勾选消息，点击“提取记忆”。
2. 后端只处理本次选中的消息，返回候选的类别、正文、摘要、引用消息 ID 与原文证据；**预览不写入 `memories`**。
3. 用户删除不想保存的候选、修正内容或类别，点击“确认保存”。
4. 后端校验证据仍对应已归档消息，生成 embedding 并写入记忆。保存后在记忆库中可见。

### C. 选择范围并检索

1. 用户输入问题，可选择平台、某些对话、记忆类别及时间范围；默认检索当前 scope 内所有活跃记忆。
2. 后端先过滤范围，再执行关键词与向量召回、融合排序、Token 预算选择，返回候选轨迹和带出处的上下文。
3. 网页展示“找到的候选”和“最终选中的记忆”两个数量。用户可取消勾选某些记忆，重新组装最终上下文。
4. 两周版本由用户主动复制上下文，Agent 可通过 MCP 搜索记忆；后续扩展可增加“插入到当前聊天输入框”。插入不等于自动发送。

### D. 更新与删除

明确的新决策可替代旧记忆，旧版本保留为 `superseded`，默认检索不再使用。用户要求忘记某条记忆时执行硬删除。删除整段对话时，连带删除其消息、由这些消息产生的记忆及相关轨迹引用；删除后页面不能再展示这些正文。

## 5. 网页信息架构

| 页面 | 首要任务 | 关键内容 |
| --- | --- | --- |
| 对话（首页） | 跨应用查看用户保存的对话 | 平台筛选、标题、采集时间、消息数、采集完整度、提炼记忆数 |
| 对话详情 | 查原文并选择性提炼 | 按顺序展示消息；勾选消息；右侧展示候选/已确认记忆及证据 |
| 记忆库 | 管理提炼结果 | 类别、状态、来源平台/会话、原文证据、版本关系 |
| 记忆检索 | 按用户指定范围找回记忆 | 查询、范围过滤、候选解释、Token 预算、最终上下文选择 |
| 召回记录 | 复查实际执行过程 | 排名、通道、取舍原因、耗时与 Token 使用 |

之前生成的 UI 概念图展示的是“记忆检索”页，不应作为整个产品的首页。图中的文档、分数和日期都是视觉占位内容，正式网页只能展示真实归档与检索结果。

## 6. 隐私、边界与验收

- 首版为**显式采集、显式提炼、显式注入**；没有用户操作，不后台同步所有聊天记录。
- 平台与会话 ID 用于去重和来源显示；不存登录 Cookie、网页账号密码或第三方会话凭据。
- 跨 scope 的对话、消息、记忆和轨迹不可互查。scope 不是认证；公网部署还需身份认证与访问控制。
- 抽取失败不影响已确认的原始归档；归档不完整要在网页标出。
- 两周最小端到端验收：导入仓库中一段带来源的样例对话 → 网页查看原文 → 选择消息并预览候选 → 用户确认 → 按平台/会话过滤检索 → 点击记忆回到原消息 → 手动选择最终上下文 → Agent 经 MCP 搜索到同一份记忆。无需浏览器扩展即可复现。

## 7. 与当前仓库的差距

当前 `python/yanji/` 与 `web/` 主要是骨架。原 API 契约只有记忆对象，缺对话、消息、预览确认及范围筛选。新增数据和接口详见 `api-data-contract.md`。开发顺序为：样例/手动对话归档与网页列表 → 选择性提炼 → 网页检索与出处 → MCP 记忆读写 → 混合检索与评测 → 浏览器扩展。扩展启动后先做一个站点的可靠闭环，再扩到其他站点。
