# 言迹 ContextTrace：14 天团队开发计划

> 从实际开工日记为 D1，连续执行 14 天。团队成员：队长（Python 引擎、seekdb、接口、评测）、前端 A（网页控制台）、前端 B（样例导入、MCP/Skill 接入、文档）。

## 两周交付目标

在真实 seekdb 上跑通“手动导入/宿主导出的原始对话 → 网页查看和选择性提炼 → 用户确认记忆 → 网页检索与溯源 → MCP 工具检索/写入同一份记忆”，再补混合检索、预算选择和可复现评测。**网页与 MCP 是两周必做闭环；浏览器扩展在两者完成且验收通过后再开发，不计入两周必做验收。** 不依赖浏览器扩展也能从仓库样例复现完整流程。

## 每日协作节奏

1. 开工前用 10 分钟同步：昨天完成什么、今天交付什么、当前阻塞是什么。
2. 当天的接口或数据结构变更，由修改者同步给另外两人；前端 mock 数据与真实 API 保持同一格式。
3. 收工前演示当天验收项，把执行命令、环境、结果和未解决问题记入 `docs/RESULTS.md`；把 AI Coding 的使用与人工验证记入 `docs/AI_USAGE.md`。
4. `main` 保持可演示。实验走独立分支；提测使用 tag 或固定 commit。

## 进度落后时的取舍

优先保住 D7 的网页 + MCP 真实闭环与 D12 的真实评测。控制台先完成对话详情、候选确认、记忆检索与出处；召回记录和版本页可在核心闭环后完善。浏览器扩展、PDF/Git 全量解析、复杂自动冲突判定与成本看板排在必做功能之后。**浏览器扩展不占用 D1–D14 的必做工时；若提前完成且通过验收，再启动扩展适配。**

队长在 **D1 定接口、D7 验闭环、D12 锁定评测口径、D13 冻结功能**。每个阶段都以可运行成果验收。
